# 第29章 セルフホスト v2（第一段：構文と意味づけの移植）

> **この章のゴール**
> Polonium 版コンパイラ（`selfhost/`）に **v2 の機能を教える**。
> 同じソースから **C 版と 1 バイト違わない IR** が出るところまで戻す。
>
> ```bash
> $ ./build/poloniumc      -S tests/cases/raises_multi.po > c.ll
> $ ./build/stage1-codegen    tests/cases/raises_multi.po > m.ll
> $ diff c.ll m.ll && echo "一致"
> 一致
> ```

第21章で `own` / `mut` を移植したときと同じ手順です。**構文 → 意味づけ → 生成**の順に、
C 版で固まったものだけを移します。

**★ この章で移すのは第27章（`raises`）と第28章（`rc[T]`）です。**
所有権の検査（第22〜24章）と解放の挿入（第25章）は**次の一段**に回しました。
理由は §29.6 に書きます。

## 29.1 何を移すか、何を移さないか

| 機能 | 章 | この章で移植 | 比較に使えるか |
|---|---|---|---|
| `own` / `mut` の構文 | 21 | 済（第21章） | ✅ |
| **`raises` / `try` / `except` / `raise`** | 27 | ✅ **この章** | ✅ トークン / AST / 診断 / IR |
| **`rc[T]` と自動デリファレンス** | 28 | ✅ **この章** | ✅ 同上 |
| 所有権の検査（`ownck`） | 22〜24 | ❌ 次の一段 | — |
| 解放の挿入（`--drop`） | 25 | ❌ 次の一段 | — |

**★ 移植の順序は「比較できる順」です。**
`tests/selfhost.sh` はトークン → AST → 診断 → IR の 4 段で C 版と突き合わせます。
**構文だけ移せば AST の比較が復活し、意味づけまで移せば診断の比較が復活します。**
段ごとに緑を取り戻せるので、どこで壊れたのかが常に分かります。

## 29.2 構文の移植

`selfhost/ast.po` / `parser.po` に足したもの：

| # | 足したもの |
|---|---|
| ① | `TY_RC`（= 8。C 版の enum と同じ値）と `type_rc` / `type_name` / `type_equal` |
| ② | `ND_TRY` / `ND_EXCEPT` / `ND_RAISE`（= 29 / 30 / 31。C 版と同じ値） |
| ③ | `Node.err_types` / `can_fail` / `err_tag` |
| ④ | `raises` 節・`try` / `except` / `raise` の構文解析と `raises_type` |
| ⑤ | `--dump-ast` の出力（`(try` / `(except` / `(raise` / `(raises`） |

**⚠️ 定数の値を C 版と一致させること。** `ND_TRY: int = 29` のように**数字で**
書いてあるのは、両実装が同じ意味づけを共有するためです。ずれると
「同じ AST に見えるのに違う木」という最悪のバグになります。

`rc[Node]` の**構文解析は 1 行も要りませんでした**。`type_ref` が
`名前 [ 要素型 ]` の形を既に読めるからです（`list[T]` と同じ道）。
**型を 1 つ足すのに構文が要らない**——第10章の設計がここでも効いています。

---

## 29.3 つまずき：`raises` はキーワードなのでフィールド名に使えない

C 版は `Node.raises` というフィールド名を使っています。同じ名前で書いたら：

```
error: クラスの中に書けるのはフィールドとメソッドだけです
 406 |     raises: Node | None
     |     ^^^^^^ ここには書けません
```

**⚠️ Polonium 版のコンパイラは Polonium で書かれています。**
`raises` は第21章で予約したキーワードなので、**フィールド名には使えません**。

```python
    # ⚠️ 'raises' はキーワードなのでフィールド名に使えません（C 版は raises）。
    err_types: Node | None  # ND_FUNC : raises 節の型注釈の並び
```

**★ 自分の言語で自分を書くと、言語の制約が実装に跳ね返ります。**
これはセルフホストの本質的な性質で、第16章から何度も出てきた「自分で自分を縛る」感覚です。
名前が違っても **IR は同じ**なので、比較には影響しません。

## 29.4 意味づけの移植

`selfhost/sema.po` に移したもの：

- エラー型 ID の割り当て（`err_classes` のリスト。**登録順が ID 順**）
- `try_catches` / `func_declares` / `check_can_fail`（R1 / R2）
- `try` / `except` / `raise` の文検査、`main` の `raises` 禁止（R4）、無意味な `try` の警告（R5）
- `rc[T]` の型解決・`rc(x)`・自動デリファレンス（`auto_deref`）
- `always_returns` に `raise` を追加

**⚠️ 診断コードまで一致させる必要があります。**

```
C 版   : error[E-RAISE-1]: 失敗しうる呼び出し 'read' を処理していません
stage1 : error: 失敗しうる呼び出し 'read' を処理していません     ← 不一致！
```

C 版は第22章で `Diag.code` を足していました。Polonium 版の `diag.po` にも
同じフィールドと `error_code_full` / `warn_full` を足して、初めて一致します。
**「メッセージ全体を比べる」（第18章の判断）は、こういう小さな差を確実に捕まえます。**

**⚠️ `list` にまだ `pop` がありません。** `try` のスタックを配列で持つとき、
C 版は `stack--` で済みますが、Polonium 版は「最後の 1 つを外した新しいリストを作る」
必要があります（`module.po` が第13章で同じ手を使っていました）。

```python
def try_pop(xs: list[ast.Node]) -> list[ast.Node]:
    out: list[ast.Node] = []
    i: int = 0
    while i < len(xs) - 1:
        out.append(xs[i])
        i = i + 1
    return out
```

**★ 「無い機能は、あるもので書く」。** `pop` を足すのは簡単ですが、
それは言語の変更であって移植ではありません。**移植中に言語を変えないこと。**

## 29.5 生成の移植

`selfhost/codegen.po` に移したもの：

- `%pl.err` の型定義、`%err.slot`、`%err.out` 引数
- 失敗しうる呼び出しのタグ検査と分岐、`unreachable` の経路
- `try` の振り分けと `except` の本体、`raise`、伝播ブロック
- `rc(x)` の生成と自動デリファレンス、`elem_is_ptr` などの型の分岐
- `declare` にエラー出力引数を足す（別モジュールの `raises` 関数）

**結果：C 版と 1 バイト違わない IR が出ます。**

```bash
$ diff <(./build/poloniumc -S tests/cases/raises_multi.po) \
       <(./build/stage1-codegen tests/cases/raises_multi.po)
（差分なし）
```

**★ ここまで来ると `# STAGE1-SKIP:` を外せます。** 第27章で
「stage1 が読めないケースは比較から外す」ために作った印を、
移植できたケースから順に外していく——**印は借金で、返すのがこの章です。**

## 29.6 なぜ検査と解放を後回しにしたのか

所有権の検査（`ownck`）と解放の挿入（`--drop`）は、まだ移していません。

**🤔 移さなくても比較は緑になる**

`tests/selfhost.sh` が比べるのは**既定の出力**です。所有権の検査は
**警告**（既定で出るが `--check` では走らせない。第22章 §22.2）、
解放は **`--drop` を付けたときだけ**（第25章 D16）。
どちらも既定の IR を変えないので、**移植しなくても比較は一致します**。

**🤔 では、いつ移すのか**

順序に理由があります。

```
  ① 構文と意味づけの移植（この章）      ← 比較が完全に戻る
  ② selfhost/ 自身を rc[T] で移行        ← 228 件を片付ける
  ③ ownck と解放の移植                   ← stage1 も自分で検査できるようになる
  ④ 既定を on にする                     ← v2 の完成
```

**②を先にやる理由**：`selfhost/` がまだ v2 の規則を満たしていないのに `ownck` を
移植すると、**stage1 が自分自身をコンパイルするときに大量の警告を出します**。
それは「移植が正しいか」の判定を邪魔します。**直してから検査を移す**ほうが、
どちらの問題かを常に切り分けられます。

**⚠️ この判断は第22章の D10（検査はまず警告で入れる）と同じ形です。**
「新しいものを入れる」と「古いものを直す」を、絶対に同じ手順に混ぜない。

## 29.7 動作確認

```bash
$ make test
全 385 件パス
全 11 件が AddressSanitizer で問題なし
トークン列一致 425 件 / AST 一致 383 件 / 型検査 一致 236 件 / IR 一致 236 件

$ make bootstrap
★ stage2 と stage3 が出す IR が完全一致（14 本）
★ 不動点に到達しました（stage2 == stage3）

$ make bootstrap-test
全 340 件パス
（45 件スキップ：所有権検査と `--drop` を使うケース。③ の移植で外せます）
```

**★ `raises` と `rc[T]` を使うテストが、比較の対象に戻りました。**
第27章では 10 件を `# STAGE1-SKIP:` で外していましたが、いまは 0 件です
（`--drop` を使う 3 件だけ、`# STAGE0-ONLY:` のまま残しています）。

**★ そして不動点は保たれています。** `selfhost/` を 5 ファイル・約 400 行
書き換えても、stage2 と stage3 が出す IR は完全に一致します。

## 29.8 まとめと次章の予告

この章でやったこと：

- v2 の構文（`raises` / `try` / `except` / `raise` / `rc[T]`）を Polonium 版へ移植した
- 意味づけ（エラー型 ID・4 つの検査・`rc` の型付け）を移植し、**診断コードまで一致**させた
- 生成（エラー ABI・振り分け・`rc`）を移植し、**IR がバイト単位で一致**した
- `# STAGE1-SKIP:` の借金を返した
- **不動点を保ったまま**、両方のコンパイラを v2 に進めた
- 検査と解放の移植は、**`selfhost/` の移行より後**に回すと決めた（理由つき）

**残り（v2 の完成まで）**：

| 段 | 内容 |
|---|---|
| ② | `selfhost/` の 228 件を `rc[T]` で片付ける |
| ③ | `ownck` と解放の挿入を Polonium 版へ移植する |
| ④ | `--deny-*` と `--drop` を既定 on にして、`make bootstrap` が緑になることを確認する |

**★ ④ まで終われば、「自分自身を、自分の新しい安全規則でコンパイルできる」ことになります。**
それが v2 の完成であり、第30章から始まる OS 開発の出発点です。
