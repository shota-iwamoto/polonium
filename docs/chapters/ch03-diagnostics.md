```

```

   |

   |

第16章以降、Polonium でコンパイラを書くとき、あなたは Polonium の

## 3.1 良い診断の 3 要素

診断メッセージが答えるべき質問は 3 つです。

| # | 質問 | 実現方法 |
|---|---|---|
| ① | **どこで**起きたか | `ファイル:行:桁` + ソース行の抜粋 + 下線 |
| ② | **何が**問題か | 主メッセージ + 位置に付ける短いラベル |
| ③ | **どうすれば**よいか | ヒント行 + 関連する位置（note） |

第1〜2章では ① と ② の一部しかありませんでした。

```
error: ')' が必要です          ← ② が曖昧（何の ')' ？）
  --> t.po:3:1
  |
3 |                            ← ① が役に立たない（空行を指している）
  | ^
```

この章で 3 つ全部を揃えます。

### 📖 参考にした設計

Rust コンパイラ（rustc）の診断形式を参考にしています。

```
error[E0308]: mismatched types
  --> src/main.rs:2:18
   |
 2 |     let x: i32 = "hello";
   |            ---   ^^^^^^^ expected `i32`, found `&str`
   |            |
   |            expected due to this
```

rustc の診断は「業界で最も親切」と評価されており、学ぶ価値があります。
ただし**全部を真似しません**。何を採用し何を捨てたかは 3.5 節で説明します。

## 3.2 モジュールを分ける — と、そこで見つかる循環依存

### ✍️ やりたいこと

第1〜2章では診断コードが 2 か所に散っていました。

| 場所 | 中身 |
|---|---|
| `util.c` | `error_at_pos()` — ソース抜粋の描画 |
| `lexer.c` | `error_at()` — `Token` を受け取るラッパ |

これを `src/diag.c` にまとめます。

### ⚠️ ここで循環依存にぶつかる

素朴に「診断は全部 diag.c へ」とやると壊れます。

```
util.c  の xmalloc() は、確保に失敗したらエラー終了する必要がある
   ↓ error() を呼ぶ
diag.c  に error() を置くと…
   ↓ しかし diag.c は xmalloc() と StrBuf を使う
util.c  ← 循環依存！
```

```
util ──▶ diag ──▶ util      ✗ 循環
```

### 📖 解決：エラーを 2 種類に分ける

**位置を示せるかどうか**で分けます。

| 種類 | 置き場所 | 例 |
|---|---|---|
| **位置情報のないエラー** | `util.c` の `error()` | メモリ確保失敗、ファイルが開けない、コマンドライン引数の誤り |
| **位置つき診断** | `diag.c` の `error_at()` / `diag_fail()` | 構文エラー、型エラー |

```
util ◀── diag ◀── lexer / parser / codegen      ✅ 一方向
```

`util.c` は自分のエラーを `error()` で報告し、`diag.h` を include しません。
**`util.c` が依存グラフの最下層である**という性質が保たれます。

### 🤔 これは妥協ではなく正しい分割

「低レベルの失敗」と「ユーザーへの診断」は、**本質的に別のもの**です。

- メモリ確保失敗はユーザーのミスではない → ソース位置を示す意味がない
- 型エラーはユーザーのミス → ソース位置が最重要

循環依存という技術的な制約が、**設計として正しい境界を教えてくれた**例です。
こういうときは制約に従うのが正解です。

### ⚠️ もう 1 つの依存：`diag` → `lexer`

診断は位置を示すために `Token` を受け取ります。だから `diag.h` は `lexer.h` を include します。

```c
// diag.h
#include "lexer.h"   // Token のため
#include "util.h"
```

**向きに注意してください。**

```
diag.h ──include──▶ lexer.h        ✅
lexer.h ─include──▶ diag.h         ✗ これはやらない
lexer.c ─include──▶ diag.h         ✅ .c からなら OK
```

`lexer.c` は `diag.h` を include して `error_at()` を呼びますが、
`lexer.h` は `diag.h` を include しません。**だから循環しません。**

`Token` を `token.h` に切り出せば `diag` を `lexer` から独立させられますが、
ヘッダが 1 枚増える割に得るものが少ないので採用していません。

## 3.3 Diag 構造体の設計

### ✍️ データ構造

```c
// ソース上の 1 箇所と、そこに付ける短い説明
typedef struct {
    Token *tok;
    const char *label;    // NULL なら下線だけ
} DiagLabel;

// 1 件の診断
typedef struct {
    const char *severity;  // "error" / "warning"。NULL なら "error"
    const char *message;   // 主メッセージ（必須）

    DiagLabel primary;     // 主要な位置（必須）
    DiagLabel related;     // 関連する位置（tok が NULL なら出力しない）
    const char *hint;      // "= ヒント: ..." （NULL なら出力しない）
} Diag;
```

### 📖 使い方：`= {0}` で初期化する

```c
Diag d = {0};                          // ★ 使わないフィールドは全部 NULL
d.message = "0 で除算しています";
d.primary.tok = n->rhs->tok;
d.primary.label = "この 0 で割ろうとしています";
d.related.tok = n->tok;
d.related.label = "演算子 '//' はここです";
diag_fail(&d);
```

**🤔 なぜ関数の引数ではなく構造体なのか**

引数で渡す設計だと、こうなります。

```c
// ✗ 引数が増えすぎる
error_at_full(tok, "0 で除算しています", "この 0 で…",
              related_tok, "演算子はここ", "ヒント…", NULL, NULL);
```

呼び出し側で `NULL` が並び、どれが何だか分からなくなります。
構造体なら**必要なフィールドだけ名前付きで埋められます**。

C には名前付き引数がないので、これが一番読みやすい代替です。

### 📖 API は 3 層にする

ほとんどのエラーは「位置 + メッセージ」だけで足ります。
毎回 `Diag` を組み立てるのは面倒なので、簡易版を用意します。

```c
// ① 一番簡単（第1〜2章から使っている）
_Noreturn void error_at(Token *tok, const char *fmt, ...);

// ② ヒント付き
_Noreturn void error_at_hint(Token *tok, const char *hint, const char *fmt, ...);

// ③ フル（関連位置やラベルが必要なとき）
_Noreturn void diag_fail(const Diag *d);
```

**この 3 層構成が重要です。** ③ だけを提供すると、
簡単なエラーを書くのが面倒になって、結局メッセージの質が落ちます。
**「簡単なことは簡単に、複雑なことも可能に」** を守ります。

### 📖 `diag_fmt` — メッセージの組み立て

`Diag.message` は `const char *` なので、書式を使いたいときは先に文字列を作ります。

```c
char *diag_fmt(const char *fmt, ...);   // printf 書式で文字列を作って返す
```

```c
d.related.label = diag_fmt("演算子 '%s' はここです", op_symbol(n->op));
```

実装は `sb_printf` と同じ手口（必要バイト数を測ってから確保）です。

## 3.4 描画：罫線の桁揃え

### 📖 レイアウトの規則

```
error: メッセージ
  --> file:line:col
   |
 2 | ソース行
   |     ^^^ ラベル
   |
   = ヒント: ...
```

すべての行で **罫線 `|` の位置をそろえる**のがポイントです。
そのために「行番号欄の幅」を先に決めます。

```c
static int num_width(int n) {          // 桁数を数える
    int w = 1;
    while (n >= 10) { n /= 10; w++; }
    return w;
}

static int gutter_width(const Diag *d) {
    int w = num_width(d->primary.tok->line);
    if (d->related.tok) {              // ★ 関連位置の行番号も考慮する
        int w2 = num_width(d->related.tok->line);
        if (w2 > w) w = w2;
    }
    return w;
}
```

そして**すべてのフィールドで幅 `gw + 1` を使います**。

```c
fprintf(stderr, "%*s--> %s:%d:%d\n", gw + 1, "", file, line, col);
fprintf(stderr, "%*s |\n",           gw + 1, "");
fprintf(stderr, "%*d | %.*s\n",      gw + 1, line, len, ls);
fprintf(stderr, "%*s | ",            gw + 1, "");
```

### ⚠️ なぜ関連位置の行番号まで見るのか

主要位置が 9 行目、関連位置が 12 行目だとします。
別々に幅を計算すると、2 つのブロックで罫線がずれます。

```
  --> t.po:9:5          ← 幅 1 で計算
   |
 9 | code
   |     ^
note: ...
  --> t.po:12:1         ← 幅 2 で計算
    |
 12 | code              ← 罫線がずれて読みにくい
    | ^
```

**両方の最大値を使えばそろいます。** 細かい配慮ですが、
読みやすさは細部の積み上げです。

## 3.5 関連する位置（note）— この章の主役

### 📖 問題：閉じ括弧忘れは「どこが閉じられていないか」が要る

第2章の時点ではこうでした。

```
error: ')' が必要です
  --> t.po:3:1
  |
3 |
  | ^
```

**メッセージは正しいのに、まったく役に立ちません。**
「どの `(` が閉じられていないのか」が分からないからです。

### ✍️ 解決：開き括弧のトークンを覚えておく

```c
static Node *primary(Parser *p) {
    // ★ 開き括弧のトークンを保持する
    Token *open = consume(p, "(");
    if (open) {
        Node *n = expr(p);
        expect_close(p, ")", open);    // ← open を渡す
        return n;
    }
    ...
}
```

```c
// 対応する閉じ記号を要求する。無ければ「開き記号はここ」を添えてエラーにする。
static Token *expect_close(Parser *p, const char *close, Token *open) {
    Token *t = peek(p);
    if (tok_is(t, close)) return advance(p);

    char *open_text = xstrndup(open->loc, (size_t)open->len);

    Diag d = {0};
    d.message = diag_fmt("閉じ括弧 '%s' がありません", close);
    d.primary.tok = t;
    d.primary.label = diag_fmt("ここに '%s' が必要です", close);
    d.related.tok = open;
    d.related.label = diag_fmt("対応する '%s' はここです", open_text);
    d.hint = "括弧の対応を確認してください";
    diag_fail(&d);
}
```

**この関数は汎用です。** 第8章（引数リストの `)`）と
第10章（添字の `]`）でもそのまま使えます。

### 📖 描画：別ブロックとして `note:` で出す

```c
if (d->related.tok) {
    fprintf(stderr, "%*s |\n", gw + 1, "");
    fprintf(stderr, "note: %s\n", d->related.label);
    DiagLabel rel = {d->related.tok, NULL};
    render_block(&rel, gw);
}
```

### 🤔 rustc のように 1 ブロックに 2 本の下線を引かないのか

rustc は同じ行なら 1 つのブロックに複数のラベルを描きます。

```
 2 |     let x: i32 = "hello";
   |            ---   ^^^^^^^ expected `i32`, found `&str`
   |            |
   |            expected due to this
```

美しいですが、実装は大変です。考慮すべき場合分けが多い：

- 2 つの位置が同じ行か、別の行か
- 別の行なら、間の行も表示するか（近ければ表示、遠ければ `...`）
- ラベルの文字列が横方向で重なるか
- 重なるなら、どちらを下の行に落とすか
- 下線の順序（左のものから描く）

**ブロックを分ければ、位置関係に関係なく常に正しく描けます。**

```
error: ...
  --> ... (主要位置のブロック)
note: ...
  --> ... (関連位置のブロック)
```

この教材では**分割方式を採用**します。
情報量は同じで、実装は 5 分の 1 です。

**🤔 判断基準**：診断の「情報」が伝わるかが本質で、「レイアウトの美しさ」は副次的です。
限られた章数で言語を完成させるには、こういう割り切りが必要です。
（rustc 方式に挑戦したい人には良い練習問題です。）

## 3.6 EOF の位置問題

### 📖 症状

`note:` を付けても、まだ主要位置が空行を指していました。

```
error: 閉じ括弧 ')' がありません
  --> t.po:3:1
   |
 3 |                            ← 空行。何も見えない
   | ^ ここに ')' が必要です
```

### 📖 原因

`read_file()` は**末尾に改行を保証**しています（第1章の設計）。

```
"(1 + 2\n"
        ↑ EOF はここ = 3 行目の 1 桁目 = 空行
```

だから EOF トークンは常に「最後の行の次にある空行」を指します。

### ✍️ 解決：EOF は直前の行の末尾を指す

字句解析器に「直前の行」を覚えさせます。

```c
typedef struct {
    ...
    // 直前の行（EOF トークンの位置決めに使う）
    const char *prev_line_start;
    int prev_line;
} Lexer;
```

```c
if (*lx.p == '\n') {
    // 今終えた行を「直前の行」として覚えておく
    lx.prev_line_start = lx.line_start;
    lx.prev_line = lx.line;

    lx.p++;
    lx.line++;
    lx.line_start = lx.p;
    continue;
}
```

EOF を置くときに、現在行が空なら直前の行の末尾を使います。

```c
if (lx.p == lx.line_start && lx.prev_line_start) {
    lx.line_start = lx.prev_line_start;
    lx.line = lx.prev_line;
    const char *eol = lx.prev_line_start;
    while (*eol && *eol != '\n') eol++;    // 行末を探す
    tv_push(&lx, TK_EOF, eol, 0);
} else {
    tv_push(&lx, TK_EOF, lx.p, 0);
}
```

### ✅ 結果

```
error: 閉じ括弧 ')' がありません
  --> tests/cases/err_unclosed_paren.po:2:7
   |
 2 | (1 + 2
   |       ^ ここに ')' が必要です
```

**キャレットが「ここに `)` を書くべき場所」を正確に指しています。**

### 📖 `tok->len == 0` でも下線を引く

EOF トークンは長さ 0 です。素朴に `for (i < tok->len)` と書くと下線が 0 本になります。

```c
if (under < 1) under = 1;    // ★ 最低 1 文字は引く
```

長さ 0 のトークン（EOF や、第4章の `INDENT` / `DEDENT`）は
「位置だけあって実体がない」ので、この保険が必要です。

## 3.7 予想外の展開：UTF-8 と表示幅

**この節は、当初「不要」と判断したものが必要になった記録です。**

### 📖 最初の判断（誤り）

`diag.c` を書いたとき、こうコメントしました。

```c
// ⚠️ 既知の制限：日本語などマルチバイト文字を含む行では桁がずれます。
//    現在は識別子もリテラルも ASCII のみで、コメントは行末までなので、
//    「下線を引く位置より前に日本語が来る」ケースは発生しません。
//    文字列リテラルを実装する第9章で、表示幅の計算が必要になります。
```

論理は一見正しく見えます。

- 識別子は ASCII のみ（言語仕様 2.6）
- 数値リテラルも ASCII
- 日本語が書けるのはコメントの中だけ
- **コメントは行末まで続くので、その後ろにコードは来ない**

→ だから「キャレットより前に日本語がある」状況は起きない、と考えました。

### ⚠️ 3.6 節の修正で、それが起きるようになった

EOF が「直前の行の末尾」を指すようになった結果、
**EOF がコメント行の末尾を指せるようになりました。**

```
$ ./build/poloniumc tests/cases/err_empty.po -o /tmp/x
error: 空のプログラムです。整数を 1 つ書いてください
  --> tests/cases/err_empty.po:1:37
   |
 1 | # ERROR: 空のプログラムです
   |                                     ^     ← 9 桁ほど右にずれている
```

`# ERROR: 空のプログラムです` は

- **36 バイト**（`# ERROR: ` が 9 + 日本語 9 文字 × 3 バイト = 27）
- **18 文字**
- **表示幅 27 桁**（半角 9 + 全角 9 × 2）

バイト数の 36 個ぶん空白を送っていたので、9 桁ずれていました。

### 📖 教訓

> **「この入力は起きない」という判断は、他の変更で無効になることがある。**

自分の変更（EOF の位置修正）が、自分の別の判断（UTF-8 は不要）の前提を壊しました。
**「不要」と判断した理由をコメントに書いておいたおかげで**、
症状を見た瞬間に「あの前提が崩れたのだ」と分かりました。

判断の**理由**を残すことには、こういう価値があります。

### ✍️ 解決：2 種類の「桁」を使い分ける

`Token.col` は**バイト数**です。文字列のスライスにはそれが正しい。
しかし人間向けの表示には別の数え方が必要です。

| 用途 | 数え方 | 例（`# ERROR: 空のプ`） |
|---|---|---|
| ソースのスライス | **バイト数** | 18 |
| 報告する桁番号 | **文字数** | 12 |
| キャレットの字下げ | **表示幅** | 15（半角 9 + 全角 3 × 2） |

**この 3 つは別物です。** 全角 3 文字なら「3 文字目」だが「表示幅 6」です。

```c
// s の先頭 1 文字を調べる。*bytes にバイト長を入れ、表示幅を返す。
static int utf8_char(const char *s, int *bytes) {
    unsigned char c = (unsigned char)s[0];

    if (c < 0x80) { *bytes = 1; return 1; }                       // ASCII

    if (c >= 0xC2 && c <= 0xDF && (s[1] & 0xC0) == 0x80) {
        *bytes = 2; return 1;                                      // ラテン拡張等は半角
    }
    if (c >= 0xE0 && c <= 0xEF && (s[1] & 0xC0) == 0x80 && (s[2] & 0xC0) == 0x80) {
        unsigned cp = (unsigned)(c & 0x0F) << 12 |
                      (unsigned)(s[1] & 0x3F) << 6 |
                      (unsigned)(s[2] & 0x3F);
        *bytes = 3;
        return is_wide_cp(cp) ? 2 : 1;                             // 日本語はここ
    }
    if (c >= 0xF0 && c <= 0xF4 && (s[1] & 0xC0) == 0x80) {
        *bytes = 4; return 2;                                      // 絵文字等
    }

    *bytes = 1; return 1;                                          // 不正なバイト
}
```

### ⚠️ 必ず前進させる（無限ループ防止）

```c
*bytes = 1; return 1;    // 不正なバイト：1 バイト進めて半角扱い
```

**不正な UTF-8 でも `*bytes >= 1` を保証します。**
`*bytes = 0` になる経路があると無限ループします。
**エラー表示中にコンパイラが固まるのは最悪の体験**なので、ここは厳重にします。

### 📖 全角判定

```c
static int is_wide_cp(unsigned cp) {
    return (cp >= 0x3041 && cp <= 0x33FF) ||   // かな・カタカナ・CJK 互換
           (cp >= 0x4E00 && cp <= 0x9FFF) ||   // CJK 統合漢字
           (cp >= 0xFF00 && cp <= 0xFF60) ||   // 全角英数
           ...;
}
```

**⚠️ これは簡易実装です。** 正確な判定には Unicode の
East Asian Width プロパティ表が必要で、`wcwidth()` 相当の実装になります。
日本語・中国語・韓国語のよく使う範囲を押さえれば実用上十分なので、
主要な範囲だけを列挙しています。

**キャレットが行末にぴったり付きました。** 桁番号も 37（バイト）→ 19（文字）に修正されています。

## 3.8 メッセージとヒントの書き方

### 📖 メッセージは「事実」、ヒントは「対処」

**分離するのが重要です。**

```c
// ✗ 全部メッセージに詰め込む（長くて読みにくい）
error_at(tok, "整数の除算に '/' は使えません。'//' を使ってください"
              "（'/' は float 専用です）");

// ✅ 事実とヒントを分ける
error_at_hint(tok,
              "切り捨て除算の '//' を使ってください"
              "（Polonium には暗黙の型変換がないため、'/' は float 専用です）",
              "整数の除算に '/' は使えません");
```

```
error: 整数の除算に '/' は使えません
  --> t.po:2:3
   |
 2 | 7 / 2
   |   ^
   |
   = ヒント: 切り捨て除算の '//' を使ってください（Polonium には暗黙の型変換がないため、'/' は float 専用です）
```

**メッセージを 1 行で読み切れる長さに保つ**と、一覧性が上がります。

### 📖 この章で追加したヒント一覧

| エラー | ヒント |
|---|---|
| タブ文字 | タブ幅の解釈でインデントの意味が変わるのを防ぐため禁止（半角スペース 4 個を推奨） |
| 数値の直後に文字 | 数値と識別子の間に空白が必要かもしれません |
| 整数の範囲外 | int が表せるのは -9223372036854775808 〜 9223372036854775807 です |
| 基数リテラルに数字なし | 基数 16 で使える数字は 0-9 a-f A-F です |
| `/` を整数に使用 | 切り捨て除算の `//` を使ってください |
| `**` 未対応 | 第9章で実装します（理由も添える） |
| 式が必要 | 式とは整数リテラル、または `(` で囲んだ式のことです |
| 余分なトークン | 1 つのファイルに書けるのは 1 つの式だけです（第4章で複数行に対応します） |

### ★ 「未実装」は未実装だと言う

```
error: 演算子 '**' はまだ未対応です
  --> t.po:2:3
   |
 2 | 2 ** 10
   |   ^^
   |
   = ヒント: 第9章で実装します（負の指数を実行時エラーにするため、エラー報告のランタイムが必要です）
```

**「解釈できない文字 `*`」で済ませてはいけません。**
書いた人が知りたいのは「`**` は今は使えない」ことであり、
**いつ使えるようになるか**です。理由まで書けば、待つべきか回避すべきか判断できます。

### 📖 非 ASCII バイトは 16 進で示す

```c
unsigned char c = (unsigned char)*lx.p;
if (c < 0x20 || c >= 0x7f)
    error_at(&tmp, "解釈できない文字です (0x%02X)", c);
error_at(&tmp, "解釈できない文字です: '%c'", c);
```

**`%c` で非 ASCII バイトを出すと端末で化けます。**
UTF-8 の 1 バイト目だけを出しても意味不明な記号になるだけです。
16 進なら「何のバイトか」が確実に伝わります。

### 📖 ラベルは文脈で変える

```c
d.primary.label = t->kind == TK_EOF ? "ここでファイルが終わっています"
                                    : "ここには式が来るはずです";
```

同じ「式が必要」エラーでも、**EOF かどうかで原因が全く違います。**
EOF なら「書き忘れ」、それ以外なら「余計なものがある」。
ラベルを変えるだけで、ユーザーの次の行動が変わります。

## 3.9 テストランナーを強化する

### 📖 問題：診断の細部がテストできない

第2章までは `# ERROR:` を 1 行しか見ていませんでした。

### ✍️ 解決：`# ERROR:` を複数行書けるようにする

```bash
# ERROR は複数行書ける。すべてが stderr に含まれることを要求する。

```

```bash
missing=""
nchecks=0
while IFS= read -r want; do
    [ -z "$want" ] && continue
    nchecks=$((nchecks + 1))
    printf '%s' "$compile_err" | grep -qF -- "$want" || missing="$missing
  - $want"
done <<EOF_WANT
$want_error
EOF_WANT

if [ -n "$missing" ]; then
    report_fail "$name" "エラー出力に含まれていない期待文字列があります:$missing
実際の出力:
$compile_err"
fi
```

これでテストケースにこう書けます。

```python

# ERROR: ここに ')' が必要です

# ERROR: = ヒント: 括弧の対応を確認してください
(1 + 2
```

**4 つの要素すべてが出ることを保証**できます。
失敗時は「どれが欠けているか」を表示します。

### ★ テストランナー自身をテストする

**新しい検証ロジックを書いたら、それが「落ちるべきときに落ちる」ことを確認します。**

## 3.11 なぜエラー回復をやらないのか

**v1 では最初のエラーで `exit(1)` します。** 複数のエラーを報告しません。

```
$ cat many.po
1 + * 2         # エラー 1

$ ./build/poloniumc many.po -o t
error: 式が必要です       ← 1 件目で終了
```

### 🤔 理由：エラー回復は独立した難問

複数エラーを報告するには、**エラーの後で構文解析を続ける**必要があります。
これを**エラー回復（error recovery）**といい、次の問題を解く必要があります。

| 問題 | 内容 |
|---|---|
| **同期点の決定** | エラー後、どこまでトークンを捨てて再開するか（`;` や改行、`)` まで？） |
| **偽エラーの抑制** | 1 個のミスから 10 個の無関係なエラーが噴出するのを防ぐ |
| **不完全な AST** | エラーがあった部分の AST は穴あきになる。後続パス（型検査）がクラッシュしないようにする必要がある |
| **エラーの重複排除** | 同じ場所の同じエラーを何度も出さない |

とくに 3 番目が厄介です。「穴あき AST」を安全に扱うには、
**エラーノード（`ND_ERROR`）を導入して全パスで扱う**必要があります。
これは型検査器とコード生成器の全体に影響します。

### 📖 実用上どれだけ困るか

**そこまで困りません。** 1 個直して再コンパイルすればよいだけです。

- 現代の機械では Polonium のコンパイルは一瞬
- **1 個目のエラーが原因で 2 個目以降が偽エラーになることが多い**ので、
  1 個ずつ直すほうが結局速いことも多い

### 📖 いつ実装すべきか

**第20章（セルフホスト）達成後の課題**とします。
そのころには言語が完成していて、
「エラーノードを全パスに通す」改修を安全に行えます。

**⚠️ 順序が重要です。** 言語が未完成なうちにエラー回復を入れると、
新機能を追加するたびにエラー処理も直す必要があり、二重の負担になります。
